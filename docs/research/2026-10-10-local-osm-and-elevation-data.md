# Локальные данные OSM и высот: исследование (spike)

Дата: 2026-10-10. Статус: **исследование, реализация отложена**. В репозитории ничего не менялось; всё построенное для проверок было временным и удалено.

## Вопрос

Можно ли качать данные локально вместо публичных сервисов (Overpass-зеркала дают 429/500/504 и таймауты на больших радиусах, высоты берутся по сети)? Районы любые, нужен универсальный механизм, а не набор готовых выгрузок.

Условия машины на момент проверки: свободно 16 ГБ на `/` и 9,5 ГБ на `/mnt/data`, около 4 ГБ доступной памяти, Docker есть, `osmium`/`osm2pgsql` нет.

## Часть 1. Локальный Overpass

### Что проверено

Поднят локальный Overpass (`wiktorn/overpass-api`) на выгрузке Мадрида с Geofabrik (85 МБ PBF). Реальные запросы проекта вокруг Серседильи (40.7436, −4.0576) сравнивались с публичным `overpass-api.de`:

| Запрос | Локально | Публичный |
|---|---|---|
| маршруты рядом (`out tags center`) | 0,5 с, 13 | 1,4 с, 13 |
| геометрия маршрутов (`out geom`) | 0,4 с, 4 | 6,2 с, 4 |
| остановки → маршруты (`rel(bn)`) | 0,2 с, 13 | 429 |
| граф троп, воды, леса (радиус 6 км) | 1,1 с, 3818 | 429 |
| `[bbox:]` + `around` по полилинии | 0,6 с, 25 | сеть недоступна |

Все 5 типов запросов прошли без изменений, число элементов совпало там, где публичный ответил. Значит, запросы переписывать не нужно (в коде используются `around` по точке и полилинии, `[bbox:]`, именованные наборы `.set`, `rel(bn)`, `out tags bb center`, `out geom N`, `relation(id:…)`).

### Замеры

- Импорт Мадрида: около 10 минут.
- База: 3,2 ГБ. Из них около 3 ГБ — индексы `nodes.map` (2,5 ГБ) и `ways.map` (0,6 ГБ), почти не зависящие от размера региона; сами данные ≈ ×2,4 от PBF.
- Оценка без замера: Испания (1,5 ГБ PBF) ≈ 7 ГБ базы и час-два импорта.
- Выгрузки Geofabrik, размеры PBF: Мадрид 85 МБ, Урал (fed-district) 396 МБ, Центральный fed-district 880 МБ, Испания 1,49 ГБ.
- Предупреждения `Way … not found` при импорте: отношения на границе региона обрезаются, маршрут у границы может прийти неполным.

### Подводные камни образа

- Geofabrik отдаёт PBF, образ ждёт `.osm.bz2`: нужен `OVERPASS_PLANET_PREPROCESS='mv /db/planet.osm.bz2 /db/planet.osm.pbf && osmium cat -o /db/planet.osm.bz2 /db/planet.osm.pbf && rm /db/planet.osm.pbf'`.
- С `OVERPASS_DIFF_URL=off` первая инициализация зависает на шаге «Updating» и не создаёт `/db/init_done`; пришлось создать маркер вручную и перезапустить контейнер без `OVERPASS_DIFF_URL`.
- Файлы базы принадлежат пользователю внутри контейнера, удалять их нужно через контейнер.
- Образ занимает 540 МБ (`docker rmi wiktorn/overpass-api`, если не нужен).

### Набросок универсальной схемы

- Менеджер регионов: по bbox маршрута выбирает самый маленький регион из индекса Geofabrik (`index-v1.json` с полигонами) или несколько соседних (склейка через `osmium merge`); скачивает, импортирует, держит в кэше с вытеснением давно не использованных.
- В `ENDPOINTS` первым ставится локальный адрес (включение переменной окружения), публичные зеркала остаются запасными. Кэш запросов (24 ч) работает как раньше.
- Свежесть данных равна дате выгрузки; нужно периодическое обновление региона.
- Отвергнуто: разбор PBF своим кодом (`osmium` + SQLite) — переписывание всех запросов; вырезка маленького bbox в отдельную базу — каждая база несёт те же ≈3 ГБ индексов.

### Открытые решения

1. Где хранить регионы (на `/mnt/data` мало места; от этого зависит размер доступных регионов).
2. Docker как новая зависимость скилла (у автора стоит, у других пользователей может не стоять).
3. Точка запуска: автозагрузка при планировании или отдельная команда заранее.
4. Не проверено: время импорта и размер базы на больших регионах (оценки выше — экстраполяция).

## Часть 2. Высоты

### OSM не содержит рельефа

В OSM есть только отдельные объекты с тегом `ele` (вершины, перевалы, родники, приюты). Высоты произвольной точки, профиля и изолиний нет (на скачанной выгрузке наличие не проверялось, это знание об устройстве OSM). Сейчас высоты берёт пакет `elevation` по сети (opentopodata, open-meteo, elevation-api.eu, open-elevation) с кэшем.

### SRTM плитками (проверено)

- Источник: `https://elevation-tiles-prod.s3.amazonaws.com/skadi/N40/N40W005.hgt.gz`, открыто, без ключей.
- Плитка 1°×1°: ≈10 МБ gzip, 26 МБ распакованной (3601×3601, int16 big-endian), разрешение ≈30 м. Скачивание заняло около 5 с.
- Читается стандартной библиотекой (`struct`) с билинейной интерполяцией: 10 000 точек за 0,014 с.
- Сверка с Open-Meteo в трёх точках у Серседильи: 1229 против 1244, 1734 против 1751, 1620 против 1628 м (расхождение 8–18 м; это разница моделей, точность каждой относительно эталона не проверялась).
- Ограничения: покрытие до 60° с.ш., нет океана, в SRTM бывают пропуски `−32768` (нужна обработка).
- Интеграция: новый провайдер `local_srtm` в `elevation` первым, онлайн-провайдеры запасными (интерфейс `fetch(locations)`, `host`, `max_batch` подходит).

### Copernicus DEM

- DSM (поверхность, включая кроны и крыши) по радарной съёмке TanDEM-X; 30 м (GLO-30), 90 м (GLO-90); лицензия по документации бесплатная с указанием источника (текст лицензии не читался).
- Хранение (проверено запросами): отдельный GeoTIFF (COG) на плитку 1°×1° в открытых бакетах AWS.
  - 30 м: `https://copernicus-dem-30m.s3.amazonaws.com/Copernicus_DSM_COG_10_N40_00_W005_00_DEM/Copernicus_DSM_COG_10_N40_00_W005_00_DEM.tif`
  - 90 м: `https://copernicus-dem-90m.s3.amazonaws.com/Copernicus_DSM_COG_30_N40_00_W005_00_DEM/Copernicus_DSM_COG_30_N40_00_W005_00_DEM.tif`
- Размеры: 30 м — 40 МБ у Мадрида, 23,5 МБ на 60° с.ш., 22 МБ на 66° с.ш.; 90 м — 4,9 МБ у Мадрида.
- Покрытие: север есть (N60E060 и N66E060 отдались), над открытым океаном плиток нет (404, N40W010).
- Формат: значения Float32 в метрах, внутри сжатие (по документации DEFLATE с предиктором для чисел с плавающей точкой). Стандартной библиотекой напрямую не читается: нужен `rasterio`/GDAL или свой разбор TIFF (IFD, `zlib`, предиктор) — порядка 80–100 строк, не проверено.

### Частичное чтение (HTTP Range)

Это не API, а те же файлы: запрос `Range: bytes=…` возвращает кусок сжатых байтов TIFF, а не числа. Порядок: заголовок и таблица смещений тайлов, затем байты нужного тайла (обычно 512×512), затем `zlib` и отмена предиктора. Выигрыш — сотни КБ вместо 40 МБ; сложность формата остаётся. GDAL/rasterio делает это сам через `/vsicurl/…`. Проверено было только, что заголовок читается Range-запросом (`II*`, обычный TIFF); чтение тайлов не пробовалось.

### Сравнение вариантов

| Вариант | Формат на нашей стороне | Зависимости | Сеть |
|---|---|---|---|
| SRTM `.hgt` целиком | простой массив | нет | один раз, ≈10 МБ на плитку |
| Copernicus COG целиком | сложный TIFF | `rasterio` или свой разбор | один раз, 5–40 МБ на плитку |
| Copernicus COG по Range | сложный TIFF | `rasterio` или свой разбор | мелкие запросы при каждом расчёте |
| Онлайн API (как сейчас) | JSON | нет | при каждом расчёте |

## Рекомендации

- Высоты — отдельная и значительно более простая задача, чем локальный Overpass; вести её отдельно.
- Основной источник — SRTM (простой формат, без зависимостей, соответствует правилу «только стандартная библиотека»).
- Для севера выше 60° с.ш.: Copernicus 90 м целиком (≈5 МБ) со своим разбором COG проще, чем Range-чтение; для оценки набора высоты 90 м, вероятно, достаточно. Перед решением стоит проверить разбор COG на реальной плитке.
- Онлайн-провайдеры оставить запасными: публичные бакеты могут измениться.
- Локальный Overpass — самостоятельная архитектурная задача (спека, затем план); решить пункты 1–3 из раздела «Открытые решения».
