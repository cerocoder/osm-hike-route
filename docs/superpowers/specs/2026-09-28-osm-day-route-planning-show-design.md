# Дизайн: osm-day-route-planning + osm-day-route-show (multi-mode + рельеф)

Дата: 2026-09-28
Статус: черновик на согласование

## 1. Обзор и цели

Два существующих скилла (`osm-hike-route-planning`, `osm-hike-route-show`, сейчас
черновики в `init-raw-source/`) жёстко заточены под пешие прогулки. Цель этого
раунда — обобщить их до `osm-day-route-planning` и `osm-day-route-show`,
поддерживающих **пешие и велосипедные** однодневные маршруты через единый
параметр режима, плюс:

- учёт рельефа (набор/сброс высоты, влияние на выбор пути и на оценку времени)
  для всех активностей;
- вынос всех весов/коэффициентов и правил проходимости из кода в файлы данных
  (пресеты + файл конкретного маршрута), а не хардкод;
- отказоустойчивый мульти-провайдерный модуль получения высот;
- счётчик уже размеченных в OSM маршрутов (`route=hiking`/`route=bicycle`) в
  районе — просто как информация пользователю.

**Не в этом раунде** (сознательно отложено, зафиксировано как будущее
расширение — не блокирует текущий дизайн):

- Лыжный режим (`ski`) — архитектура должна допускать его добавление позже
  через новый пресет + расширение справочника тегов, без переписывания кода
  маршрутизации.
- Третий скилл `osm-day-route-prepare` (погода, световой день, сезонные
  опасности, калории) — отдельный под-проект со своей спецификацией.
- Использование GPS-треков OSM (`/api/0.6/trackpoints`) как сигнала
  "протоптанности" — отклонено: нарушает usage policy OSM API для
  автоматизированных повторяющихся запросов и даёт более слабый и более
  чувствительный к приватности сигнал, чем уже используемые курируемые
  отношения `route=hiking`/`route=bicycle`.
- Прокладка маршрута вдоль существующего `route=*` relation целиком —
  сейчас только считаем их количество, не используем геометрию.

## 3. `osm-day-route-planning`

### 3.1 Параметры режима

- `mode`: `walk` | `bike` (ski — задокументированное будущее расширение, не
  реализуется).
- `style` (только для `bike`): `leisure` | `sport`.
  - `leisure` — как пеший: избегать шоссе, предпочитать лес/грунтовки/
    веломаршруты.
  - `sport` — предпочитает асфальт и более прямой путь, **но безопасность
    остаётся приоритетом**: трасса без вело-инфраструктуры (`trunk`/`primary`
    без `cycleway=*`) по-прежнему жёстко исключена, не просто штрафуется.

**Определение режима/стиля**: по явным словам в запросе пользователя (как
сейчас работает определение локации и типа рендера в `show`); если неясно —
спросить явно, **не выбирать `walk` по умолчанию молча** (тот же принцип,
что уже действует в `osm-hike-route-show` для параметра `type`).

### 3.2 Веса и правила проходимости — вынесены из кода в данные

Два уровня:

1. **Пресеты** (`skills/osm-day-route-planning/presets/*.json`) — данные
   скилла, read-only, один файл на комбинацию режим(+стиль):
   `walk.json`, `bike-leisure.json`, `bike-sport.json`.
2. **`weights.json` конкретного маршрута** (`routes/<slug>-<date>/weights.json`)
   — копия выбранного пресета, слитая с правками пользователя, сохраняется на
   шаге архивирования. Позволяет позже отредактировать веса и пересчитать
   маршрут без повторного "допроса" пользователя о предпочтениях.

Формат — **JSON**, не YAML: в проекте сейчас нулевые внешние зависимости
(только stdlib, включая `urllib.request` вместо `requests`), и это сознательно
сохраняется — не заводим `pyyaml` ради комментариев в конфиге.

Пресет несёт **не только веса**, но и правила проходимости — это следует из
того же принципа "не хардкодить": иначе добавление лыж потребует правки кода
маршрутизации, а не только нового пресета.

```jsonc
{
  "mode": "bike",
  "style": "leisure",

  // какие way считаются проходимыми для этого режима
  "routable_highway": ["path", "footway", "track", "cycleway", "residential", "living_street"],

  // жёсткое исключение (не штраф) — свои для каждого режима
  "hard_exclude_tags": {
    "bicycle": ["no", "dismount"],
    "highway": ["steps"]
  },
  // trunk/primary/secondary без вело-инфраструктуры — жёсткое исключение для bike,
  // не применяется для walk
  "exclude_highway_without_infra": ["trunk", "primary"],

  // барьерные узлы, блокирующие ИМЕННО этот режим (стиль/турникет проходим
  // пешком, но блокирует велосипед)
  "blocking_barrier_tags": ["cycle_barrier", "turnstile"],

  "buffers_m": { "highway": 50, "water": 30 },

  "preferences": {
    "prefer_forest": 1.5,
    "avoid_open_field": 2.0,
    "avoid_near_highway": 3.0,
    "avoid_near_water": 2.0,
    "avoid_steep_gradient": 2.5
  },
  "gradient_threshold_pct": 8,

  "pace_kmh": 15,
  "ascent_minutes_per_100m": 10,
  "duration_warning_hours": 12
}
```

Точные ключи/значения уточняются на этапе реализации — здесь фиксируется
**форма и принцип** (веса и правила — данные, код их только интерпретирует),
не финальная схема.

На шаге "elicit preferences" скилл предлагает пользователю пресет,
соответствующий режиму/стилю, как отправную точку ("вот дефолтные веса для
..., менять что-то?"), сливает правки в копию, сохраняет как `weights.json`
маршрута. Сами пресеты не модифицируются.

### 3.3 Направленный граф + рельеф

Текущий `build_graph` строит **неориентированный** граф (одно ребро — оба
направления с одинаковой стоимостью). Это перестаёт быть корректным сразу по
двум причинам, независимо друг от друга:

- **oneway для велосипеда** — `oneway=yes` с исключениями
  (`oneway:bicycle=no`, `cycleway=opposite*`) уважается для `bike`, не для
  `walk`.
- **асимметрия уклона** — подъём и спуск по одному и тому же ребру стоят
  по-разному (и в весах маршрута, и в оценке времени по правилу Нейсмита) —
  это верно для **любого** режима, как только появляется рельеф.

Изменение: `build_graph` строит направленный граф — каждое физическое ребро
превращается в два направленных ребра со своей стоимостью. Правила oneway —
часть пресета режима (см. 3.2), не хардкод. Порядок обхода путевых точек
(2-opt) должен учитывать, что перестановка меняет стоимость несимметрично.

### 3.4 Модуль высот (`scripts/elevation/`)

**Провайдеры** (исследованы факты по каждому — см. таблицу ниже), все
без ключа, batch по координатам, порядок-сохраняющий ответ:

| Провайдер | Запрос | Батч | Лимит free | Датасет |
|---|---|---|---|---|
| Open-Topo-Data | `GET /v1/<dataset>?locations=lat,lon\|...` | 100 | 1000/день, 1 req/s | SRTM 30/90м |
| Open-Meteo | `GET /v1/elevation?latitude=..,..&longitude=..,..` | 100 | не документирован, провайдер надёжный | Copernicus GLO-90, 90м |
| Elevation-API.eu | `GET /v1/elevation?pts=[[lat,lon],...]` | не документирован (считаем 100) | 10 req/s | Copernicus (ESA) |
| Open-Elevation | `POST /api/v1/lookup {"locations":[...]}` | без строгого лимита | нестабилен (известные таймауты) | не публикуется |

Порядок обхода при отказе: Open-Topo-Data → Open-Meteo → Elevation-API.eu →
Open-Elevation (последний — наименее надёжный, только "на подхвате").

**Интерфейс** (`providers/base.py`): `ElevationProvider` — `provider_id`
(уникальный слаг, например `open_topo_data`), `max_batch`, `rate_limit_per_sec`,
`fetch(locations: list[(lat, lon)]) -> list[float | None]`. Один источник —
один файл в `providers/`. Список провайдеров — явный в `__init__.py`, без
авто-discovery по файловой системе (простой список даёт ту же расширяемость
без лишней магии).

**`ElevationService.get_elevations(locations)`**:
1. Проверка кэша (округлённые координаты).
2. Для промахов — разбить на батчи по `max_batch` текущего провайдера,
   соблюдая `rate_limit_per_sec`.
3. При ошибке батча (не-200, таймаут, битый ответ) — перейти к следующему
   провайдеру **для непокрытых точек**.
4. Если все провайдеры отказали — точка получает `None` (ребро не
   штрафуется за уклон), предупреждение в stderr, не исключение.
5. Кэш пишется инкрементально после каждого успешного батча (тот же урок,
   что уже есть в `osm-hike-route-show` про `wiki_links.json` — не терять
   прогресс при обрыве на середине).

**Кэш — общий, не по-маршрутный**: `routes/.cache/elevation.json`
(высоты запрашиваются до появления папки маршрута, и один район
переиспользуется между разными маршрутами). Ключ: округлённые координаты +
`dataset`. Каждая запись хранит `provider_id` и `dataset`, отдавшие значение:
```json
{"lat": 55.1, "lon": 60.2, "elevation": 340.5, "provider_id": "open_topo_data", "dataset": "srtm90m"}
```

**Сэмплирование вместо "высота на каждый узел"**: узлы OSM стоят через
5-20м — плотнее, чем разрешение любого датасета (30-90м), так что запрос
высоты на каждый узел — точность, которой в данных всё равно нет. Вместо
этого:
1. Каждый путь в отфильтрованном графе сэмплируется точками через ~150м
   (параметризуемо).
2. Высота запрашивается только для сэмплов.
3. Высота любого графового узла между сэмплами — линейная интерполяция по
   расстоянию вдоль пути.
4. Уклон ребра = разность интерполированных высот узлов / длина ребра.

**Смешение провайдеров внутри одного расчёта не исключается, а принимается
как есть** — гарантировать "один провайдер на весь граф" нереалистично при
последовательных батчах и отказах на полпути. Поскольку сэмплы уже редкие
(150м) и соседние сэмплы относятся к одному пути, шов между двумя
провайдерами — редкий и не катастрофический случай (расхождение датасетов на
соседних точках — обычно единицы метров). Провайдер/датасет каждой точки
логируется в кэше (см. выше) для отладки, но не блокирует смешение.

### 3.5 Оценка времени в пути

Базовый темп (`pace_kmh` из весов) + штраф за набор высоты
(`ascent_minutes_per_100m`, в духе правила Нейсмита), считается по
интерполированному профилю высоты вдоль решённого пути. Если оценка
превышает `duration_warning_hours` (эвристический общий порог, без знания
даты/сезона/широты) — мягкое предупреждение в выводе: маршрут может не
влезть в световой день в зависимости от сезона, для точной проверки —
будущий `osm-day-route-prepare`. Не блокирует построение маршрута, даже если
оценка больше 24 часов.

### 3.6 Счётчик размеченных маршрутов

В `fetch_area_data` добавляется лёгкий запрос:
`relation["route"~"hiking|foot"]` для `walk`, `relation["route"~"bicycle|mtb"]`
для `bike`, в радиусе поиска. Геометрия не используется для маршрутизации —
только подсчитывается количество и добавляется в итоговую сводку пользователю
и в `notes.md`: например, "В этом районе размечено N публичных маршрутов
(route=hiking) в OSM".

### 3.7 Схема `route.geojson` — дополнения

- Координаты геометрии (`LineString` и `Point`) становятся 3-мерными:
  `[lon, lat, ele]` — стандартный GeoJSON, что попутно даёт `<ele>` в GPX без
  отдельных полей.
- Новые свойства `LineString`-фичи (посчитанные результаты, не входные
  данные — не дублируют `weights.json`):
  - `mode`, `style`
  - `distance_km`
  - `elevation_gain_m`, `elevation_loss_m`
  - `duration_estimate_hours`
  - `duration_warning` (строка или `null`)
  - `curated_routes_count`

Явное разделение: **`weights.json` хранит входные данные для воспроизведения
запуска** (режим, стиль, веса, правила), **свойства `LineString` хранят
посчитанные результаты** (дистанция, время, набор высоты, предупреждение).
Не дублировать между ними.

## 4. `osm-day-route-show`

### 4.1 Правки под 3D-координаты

Три места в `render_map.py` распаковывают `[lon, lat]` как пару и упадут на
`[lon, lat, ele]`:

- `build_gpx`: `for lon, lat in line["geometry"]["coordinates"]` — переписать
  на извлечение `ele`, если есть, и писать `<ele>` в `<trkpt>`/`<wpt>`.
- `resolve_wikipedia`: `lon, lat = feature["geometry"]["coordinates"]`.
- `_wiki_cache_key`: та же строка.

`bbox_center_zoom` и Leaflet-рендер (`pointToLayer`, GeoJSON layer) правок не
требуют — там либо индексация по `[0]`/`[1]`, либо Leaflet сам поддерживает
высоту как третью координату.

### 4.2 Отображение новых полей

Сайдбар получает блок "Статистика маршрута" из структурированных свойств
`LineString` (`mode`, `style`, `distance_km`, `elevation_gain_m/loss_m`,
`duration_estimate_hours`, `duration_warning`, `curated_routes_count`) —
именно из свойств фичи, не парсингом `notes.md` (надёжнее, не требует
расширения `SECTION_ALIASES`).

### 4.3 Обратная совместимость

Архив без `mode` в свойствах (маршрут, построенный до этого раунда)
трактуется `show` как `walk` — без ошибок.

## 5. Тестирование

- Юнит-тесты `ElevationService` с фейковыми провайдерами: частичный отказ →
  переход к следующему провайдеру для непокрытых точек, кэш-хиты не бьют по
  сети повторно, разбиение на батчи по `max_batch`, соблюдение
  `rate_limit_per_sec`.
- Тест сэмплирования/интерполяции высоты (сэмплы через ~150м, интерполяция
  между ними, уклон на границах сэмплов).
- Тест загрузки и валидации пресетов (обязательные ключи, разумные типы).
- Тест направленного графа: oneway соблюдается для `bike`, не влияет на
  `walk`; асимметричная стоимость подъём/спуск.
- По одной проверке на реальных данных на каждый режим (по аналогии с
  существующей проверкой на исключение военных объектов у Куатро-Вьентос):
  один прогон `walk`, один — `bike` (оба стиля, если время позволяет).
- `osm-day-route-show`: рендер архива с 3D-координатами не падает; рендер
  старого архива без `mode` в свойствах не падает (fallback на `walk`).

## 6. Открытые вопросы / будущие расширения (не блокируют этот раунд)

- Лыжный режим (`ski`): пресет + расширение справочника тегов
  (`piste:type`, беговые/горные лыжи), тестируется, следует ли текущей
  инфраструктуре в 3.2–3.4 без переписывания кода маршрутизации.
- `osm-day-route-prepare`: погода, световой день (точная проверка по дате и
  широте вместо эвристического `duration_warning_hours`), сезонные опасности,
  калории — отдельная спецификация.
- Прокладка маршрута вдоль существующего `route=hiking`/`route=bicycle`
  relation целиком (сейчас — только счётчик, без использования геометрии).
